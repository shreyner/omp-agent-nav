# Работа в omp-agent-nav

## Перед изменениями

- Прочитай применимые skills текущей сессии.
- Начни с [spec/README.md](spec/README.md), затем прочитай требования, которых касается задача.
- Перед правками проверь состояние файлов. Для текущей задачи пользователь разрешил работу в основной папке без development worktree; продуктовые инструменты worktree остаются частью v1.
- Архитектура v1 — расширение обычного установленного omp версии из проверенной матрицы (18.11.0, 18.11.1; миграция с 18.10.3 2026-10-15, матрица 2026-10-16), подключаемое через `extensions` в конфигурации. Отдельного launcher, копии CLI, fork и изменений установленного пакета, его зависимостей или исходного checkout omp нет.
- Для интеграционной проверки запускай обычный `omp` с расширением через временную конфигурацию или `-e`. Host imports проходят штатный bundle shim; file URL разрешён только для явно выбранных library helpers, которыми владеет расширение. Совместимость выбранной версии проверяет `src/runtime.ts`.
- Проверки прежнего launcher — исторический baseline. Текущую поставку подтверждают отдельные bundled runtime/память/TUI/RPC сценарии; source-test harness не заменяет их.

## Документация вместе с кодом

- В той же правке обновляй затронутые контракты в `spec/behavior.md`, механику в `spec/mechanics.md` и проверки в `spec/verification.md`.
- Таблица `spec/README.md` связывает требование, код, проверку и фактический статус. Наличие кода не означает, что все интеграционные сценарии проверены.
- Сохраняй ID требований, проверок, допущений и будущих возможностей; не переиспользуй ID для другого смысла.
- Подтверждённые факты выноси из непроверенных допущений в behavior/mechanics. Проверки снабжай датой, командой или способом и границей доказательства.
- Техдолг добавляй только после проверки и сознательного решения пользователя отложить исправление. Закрытую запись удаляй целиком.
- Следующие этапы веди в `spec/future-features.md`. Принятая граница v1: main сохраняет загруженные JS/TS extensions/custom tools при переезде; полная перезагрузка factories — F7.

## Проверки

- Запускай focused `bun test ./test/<затронутые файлы>` и `bun run check`. Check — сборка Bun с external packages плюс статический гейт `biome check --error-on-warnings .`; проверкой TypeScript compiler он не является.
- Стиль кода держит Biome 2.5.15: `bun run lint`, `lint:fix`, `fix:unsafe`, `format`, `format:check`; `bun run matrix` прогоняет версии omp. `fix:unsafe` запускай только с ревью диффа — unsafe-фикс уже ломал тип в тесте (2026-10-16). Гейты: `useBlockStatements` (фигурные скобки обязательны), `noExcessiveCognitiveComplexity` с бюджетом 15 (новая функция выше — выноси хелпер), `useSortedInterfaceMembers` (assist сортирует члены интерфейсов). Отключены осознанно: `noNamespaceImport` (namespace-импорты node-builtin'ов — принятый стиль кода), `noExplicitAny` и `noNonNullAssertion` (cast-стиль апстрима pi). Конфиг — [biome.json](biome.json). Мост разложен по модулям: [src/host/](src/host) (`bridge`/`coordinator`/`grants`/`mcp`), [src/host.ts](src/host.ts) — тонкий реэкспорт публичной поверхности.
- В `node_modules` лежит только `@biomejs/biome`; omp объявлен optional peer — иначе `bun install` притягивает установленный хост в репозиторий и ломает PATH-резолв omp тестами и матрицей.
- Полные проверки проекта выполняются через `bun run test`. Не заменяй behavioral tests поиском строк исходника и не используй `mock.module()`.
- Git, session storage, LSP и память проверяй во временных fixtures; пользовательские worktree, банки и настройки не использовать как расходные данные.
- Отдельно различай штатный LSP workspace checker `file:"*"` и запросы `*.go`, которые идут через gopls.
- После изменения документации проверяй UTF-8, fences, JSON-примеры, local links/anchors и соответствие параметров коду.

## Границы действий

- Не инициализируй Git, не устанавливай зависимости и не меняй глобальную конфигурацию автоматически. Не запускай upstream `bun setup/install`: prepare-hook может менять сгенерированные исходники и глобальные ссылки.
- Не коммить, не пушь и не публикуй автоматически. Не добавляй `Co-Authored-By`.
- Постоянный контекст реализации хранится в `spec/*.md`.
