# Поведение и интерфейсы v1

Инструменты регистрирует [расширение](../src/index.ts); [bridge](../src/host.ts) обеспечивает операции сессии через штатные механизмы omp версии из проверенной матрицы.
Способ поставки — `extensions` в конфигурации обычного omp или его флаг `-e`; отдельного launcher нет. Фактические проверки описаны в [verification.md](verification.md#bridge-probe).
Параметры и типы результата определены в [types.ts](../src/types.ts).

<a id="relocation"></a>
## Основная сессия

`session_move {dir}` переводит основную сессию в существующий разрешённый каталог, сохраняя session ID и историю (NAV-01).
Абсолютный путь и `~`/`~/...` поддерживаются; относительный dir вычисляется от cwd при принятии запроса.
После applied актуальны cwd, хранилище сессии, AGENTS/context/rules, settings, skills, commands/prompts, проектные MCP, LSP и память (NAV-04).
Проектный MCP цели, как и при штатном старте omp, переезд не блокирует: поднявшиеся серверы публикуются, MCP prompt-команды прежнего проекта снимаются, а сбой или незавершённый за 30 с старт попадает в итог `applied` полем `warning` (решение пользователя 2026-10-19; до него переезд откатывался). `/nav-move` показывает warning человеку. Память остаётся обязательной: её сбой откатывает переезд. Для `task.cwd` MCP цели остаётся строгим ([сабагенты](#task)).
<a id="system-md"></a>Граница v1: `SYSTEM.md` и `SYSTEM_TEMPLATE.md` (проектные и пользовательские) omp находит один раз при запуске (`main.ts`) и после переезда не перечитывает. Пока сессия не перезапущена, действует override стартового каталога; override цели не подхватывается. До 2026-10-19 расширение перерисовывало prefix собственным клоном рендерера. Клон удалили по решению пользователя: проектные `SYSTEM.md` не используются, а клон расходился с хостом на каждой версии.

Основная сессия сохраняет уже загруженные JS/TS extensions/custom tools, включая навигацию. Новые фабрики B при переезде не загружаются; фабрики A не выгружаются.
Это принятая граница v1 и не запрещает переезд: см. [TD-01](tech-debt.md#td-01) и [F7](future-features.md#f7).
AGENTS проекта, разрешённого грантом (`workspace_grant`, подтверждение `session_move`), к выбранному проекту не добавляются: гранты определяют только доступ. Каталоги штатного `--add-dir`/`/add-dir` работают как в штатном omp: их AGENTS и workspace tree входят в prompt (решение пользователя 2026-10-19, см. [разрешения](#permissions)).

<a id="results"></a>
## Результаты и ошибки

Меняющие состояние инструменты сначала возвращают receipt **queued**. После пакета bridge применяет запрос до следующего обращения к модели и сохраняет итог **applied**, **failed** или **cancelled** (NAV-02).
Итог записывается как developer-message в runtime и session JSONL; новый пользовательский ввод не требуется. Каждый следующий запрос к модели, в том числе в следующих прогонах, содержит этот итог ровно один раз.

`WorkspaceResult` содержит `id`, `status`, `action`; необязательные `target`, `cwd`, `error`, `result`, `warning` дополняются по операции (`warning` — у applied move/enter/exit, когда проектный MCP цели поднялся частично).
Для create/remove result.path — фактический canonical путь. Create также возвращает branch, baseCommit, mainRoot и данные штатного clone backend.
Queued create ещё не означает, что каталог и ветка созданы. Ошибка принятия запроса выбрасывается сразу; ошибка применения появляется в сохранённом итоговом result.

Navigation различает invalid, unavailable, permission, conflict, git и busy. Неполный rollback записывает обе ошибки и фактический cwd, затем останавливает следующий запрос провайдеру.

<a id="core-api"></a>
## Context API bridge (NAV-07, снято)

До 2026-10-19 расширение добавляло в context методы `ctx.requestWorkspaceChange` и `ctx.listWorktrees` через обёртку `ExtensionRunner.createContext`. Их вызывали только собственные инструменты и команды расширения, у которых bridge и так есть в замыкании, поэтому обёртку удалили. ID NAV-07 не переиспользуется.

Инструменты и `/nav-move` ставят запрос в coordinator основной сессии напрямую: `bridge.coordinator(ctx).request(...)`, список читает `coordinator.navigation.listWorktrees()`.
Union запросов: `{action:"move",dir}`, `{action:"create",branch,path?,ref?}`, `{action:"enter",path}`, `{action:"exit"}`, `{action:"remove",path}`. Request возвращает queued receipt; list читает реестр сразу.
Вложенный вызов изменяющего инструмента отсекает допуск по tool ID ([пакеты](#batch)); `worktree_list` только читает. TUI, print и RPC используют тот же coordinator — [V06](verification.md#v06).

<a id="batch"></a>
## Одиночный пакет и сабагенты

Шесть изменяющих инструментов (включая `workspace_grant`) должны вызываться напрямую, по одному в пакете (NAV-03).
`agent.beforeToolCall` проверяет весь пакет модели: move + write и две мутации блокируются до любых эффектов, независимо от порядка вызовов.
В v18.11.0 нет нового core-поля requiresSoloBatch: эквивалентную проверку выполняет bridge.
Допущенный прямой tool ID нужен execute; вложенный wrapper и делегированный context не могут обойти проверку.

Все семь инструментов навигации доступны только основной сессии; они отфильтрованы у сабагента, coordinator повторно проверяет agent kind.
`worktree_list` не является мутацией и не требует одиночного пакета, но также запрещён сабагенту.

<a id="busy"></a>
## Занятость и отмена

Coordinator допускает один pending/applying запрос; слот занимается уже на время валидации, поэтому параллельный второй запрос получает отказ, а не подменяет первый. Compaction и изменения session ID/cwd дают отказ или cancelled (NAV-05).
В TUI применение проходит через native `withBtwSessionMove`; активная BTW не даёт выполнить файловую операцию.
Обёртка native `runEphemeralTurn` учитывает активные `btw:*` во всех режимах и запрещает новую BTW во время apply; print/RPC защищены той же границей.
При abort, session switch или shutdown неприменённый запрос снимается. После восстановления сессии старая мутация автоматически не повторяется.
`/nav-move <dir>` доступен человеку только в idle основной сессии.

<a id="permissions"></a>
## Разрешения и пути

Допустимы стартовый проект, гранты расширения и штатные дополнительные каталоги, которые добавил пользователь: `--add-dir`, `/add-dir` (NAV-06).
Гранты хранятся только в session custom entry расширения (ledger) и в штатный список дополнительных каталогов не попадают, поэтому их AGENTS не входят в prompt. Штатный список расширение читает вживую и сравнивает после realpath, так что alias вроде `/var` → `/private/var` новых диалогов не вызывает.
Каталоги, которые штатный список получил из текущих настроек `workspace.additionalDirectories`, сами по себе корнями не считаются. После переезда это настройки проекта цели, и человек их не одобрял: иначе `.omp/config.yml` цели с `additionalDirectories: ["/"]` открыл бы навигацию везде без диалога (найдено ревью 2026-10-19). Корни, которые были в штатном списке при старте сессии (`--add-dir`, глобальные настройки и настройки стартового проекта), сразу засеваются в ledger. Поэтому они остаются корнями и после того, как settings watcher уберёт их при уходе из стартового проекта.
Посещённый путь грантом не становится. Исключение — штатный корень, в который переезжает сессия: до переезда он переносится в ledger, потому что штатный `moveTo` убирает новый cwd из списка дополнительных каталогов. Следствие: с `--add-dir B` AGENTS B видны в A до первого перехода в B, а после A → B → A уже нет — штатный `/move` ведёт себя так же.
<a id="nav-roots"></a>`/nav-roots` (NAV-10) показывает человеку корни с источником: `start`, `grant`, `add-dir`; исчезнувший помечается `missing`. `/nav-roots revoke <dir>` в idle отзывает корень, названный путём точно. Путь linked worktree вне своего primary называет primary; подкаталог корнем не является и ничего не отзывает, ответ называет покрывающий корень. Отзыв удаляет корень из ledger и из штатного списка, после чего prompt пересобирается, как после `/remove-dir`. Не отзываются стартовый проект и корень, без которого cwd, покрытый до отзыва, оказался бы вне корней. Если cwd уже вне корней (например, после штатного `/move`), отзыв разрешён. Ответ называет корень, которым путь ещё покрыт.
Отзыв B запрещает следующие операции с B и его worktree, если нет другого действующего корня. Штатный `/remove-dir` убирает только каталог из штатного списка; грант в ledger он не трогает.
Границы:
- штатный `/move` или `/wt` в корень `--add-dir` обходит расширение и убирает корень из списка. Тогда `task` без cwd и worktree-операции вне других корней получат permission-отказ с `suggestedGrants`; путь расширения — `/nav-move`;
- корень, отозванный из `--add-dir`, вернётся при следующем запуске с тем же флагом;
- корень из `--add-dir` и настроек стартового проекта засеян в ledger, поэтому штатный `/remove-dir` доступ к нему не снимает — только `/nav-roots revoke`;
- каталог, добавленный во время сессии правкой настроек (`workspace.additionalDirectories`), корнем не становится; для него нужны `/add-dir` или `workspace_grant`;
- ledger хранится по веткам дерева сессии: переход по дереву к записи до гранта или отзыва показывает состояние той ветки;
- сессии версий до 2026-10-19 держали гранты и в ledger, и в штатном списке. Для них `/remove-dir` убирает AGENTS гранта из prompt, а `/nav-roots revoke` — доступ целиком.
Исчезнувший стартовый проект (например, удалённый до resume сессии) ничего не авторизует, как и исчезнувший grant; навигация между остальными корнями работает.
Корни ограничивают только навигацию и `task.cwd`. Это не песочница: файловые и shell-инструменты omp ими не ограничены.
`workspace_grant {dirs}` — инструмент основной сессии для явного принятия существующих каталогов в workspace-корни (NAV-08).
Путь canonical-резолвится, worktree сводится к своему primary checkout. Уже принятые корни, включая стартовый проект, пропускаются со статусом skipped.
Все каталоги разрешаются до первого гранта: ошибка в любом из них не выдаёт ни одного.
Вызов выполняется после явного подтверждения пользователя: approval tier write с обязательной policy prompt — диалог сохраняется в любом режиме, включая yolo; без интерактивного UI вызов fail-closed.
Диалог показывает для каждого каталога корень, который будет выдан: `dir: <путь> → grant: <корень>`, если они различаются (symlink, worktree, `~`). Выдаётся только показанный корень: если путь к моменту выполнения ведёт в другой корень, вызов падает и ничего не выдаёт. Каталог, которого не было при показе диалога (корень не показан), тоже не выдаётся — вызов нужно повторить, когда каталог существует.
Один вызов покрывает пакет каталогов одним подтверждением; грант session-scope (только ledger расширения), отзыв — [`/nav-roots revoke`](#nav-roots).
Permission-отказ навигации или task.cwd вне корней возвращает в ошибке primary-корень цели (suggestedGrants) с подсказкой вызова; повторный запуск после подтверждения выполняет модель.

Интерактивный `session_move {dir}` при цели вне принятых корней спрашивает человека на месте: approval tier write с обязательной policy prompt — диалог переживает yolo; formatApprovalDetails показывает путь цели и корень, который будет выдан.
Подтверждение человека выполняет вызов: execute до валидации выдаёт грант корня цели через grantWorkspaceDirs (ledger, session-scope, worktree сводится к primary) и затем проходит штатный queued → applied.
Цель сравнивается с корнями после realpath: корень, выданный через `workspace_grant`, прошлое подтверждение или штатный `/add-dir`, не спрашивает повторно и тогда, когда модель передаёт symlink-алиас (macOS `/var` → `/private/var`). Worktree уже принятого проекта тоже не спрашивает. Отказ человека — штатный deny omp: вызов не выполняется.
Грант выдаётся только по решению approval и только на корень из диалога. Цель, которая после approval стала вести в другой корень (подменённый symlink), гранта не получает: вызов падает с permission-отказом или «not the approved <корень>».
Хост не запоминает решение по явной policy prompt инструмента: «approve for session» применяется только к prompt от режима. Единственная память — ledger грантов расширения.
Без интерактивного UI (print/headless, RPC без TUI-owner) диалог не строится, вызов сохраняет прежний fail-closed permission-отказ с suggestedGrants.
`.git`-путь и несуществующая цель не спрашивают: approval остаётся write, validateMove отвергает их как раньше.
Границы: отзыв между approval и execute практически исключён — `/nav-roots revoke` работает только в idle; если он всё же случится, execute выдаст показанный грант заново. Пользовательская политика `tools.approval.session_move` не снимает диалог: явный prompt инструмента сильнее пользовательского `allow`, а `deny` запрещает вызов.

Существующие пути проверяются через realpath; отсутствующая часть — через canonical существующего предка до mkdir.
Запрещены symlink escape, `.git`, отдельные gitDir/commonDir и их aliases внутри принятых корней.
Зарегистрированный worktree допускается по доказанной принадлежности разрешённому primary, а не по имени каталога.
Pure Jujutsu workspace не поддерживает инструменты worktree v1; session_move в обычный каталог остаётся доступным.

<a id="worktree-list"></a>
## `worktree_list {}`

Возвращает primary и зарегистрированные worktree текущего Git-проекта (WT-01).
Поля записи: path, primary, branch/head, detached, locked, dirty, untracked, inUse, available.
Для недоступной записи dirty/untracked равны null; путь остаётся виден. `inUse` учитывает физический и исходный cwd живых сабагентов текущего процесса.
Вне Git-проекта — диагностический отказ.

<a id="worktree-create"></a>
## `worktree_create {branch, path?, ref?}`

`branch` — **новая** Git-ветка. Существующая ветка отклоняется до файловых эффектов; она не пересоздаётся и не сбрасывается.
`ref` по умолчанию — HEAD текущего checkout, включая вызов из worktree; явный ref разрешается в commit (WT-02).
Создаётся чистый worktree без переноса dirty/untracked исходного checkout. Основная сессия остаётся в текущем cwd.

```json
{"branch":"PROJ-123_fix","path":".claude/worktree/PROJ-123_fix","ref":"HEAD"}
```

<a id="paths"></a>
### Путь и отказ создания

- Абсолютный путь, `~`/`~/...` и относительный путь поддерживаются; относительный вычисляется от primary текущего проекта (WT-03).
- Явный path используется точно, без суффикса. Без path применяется managed base omp/`worktree.base`/`OMP_WORKTREE_DIR` и штатный подбор свободного адреса.
- Цель должна отсутствовать или быть пустым обычным каталогом. Существующий пустой каталог сохраняет identity; clone для него отключён.
- Внешняя цель должна находиться внутри принятого root либо managed base. Запрещены пересечение checkout/worktree, metadata, файл, непустой каталог, dangling symlink и выход за разрешённую границу.
- Внутри primary clone отключён; точное экранированное правило добавляется в shared `.git/info/exclude`, если оно нужно (WT-04). `.gitignore` не меняется.
- На failure local exclude остаётся append-only; результат сообщает оставленное безопасное правило. Rollback не обрезает общий файл другого процесса.
- Cleanup удаляет только собственный чистый неизменённый partial и собственную неизменённую новую ветку. Чужие или изменённые данные сохраняются с диагностикой.

<a id="worktree-enter-exit"></a>
## `worktree_enter {path}` и `worktree_exit {}`

Enter принимает корень зарегистрированного linked worktree **текущего проекта**, проверяет commonDir и выполняет обычную релокацию (WT-05).
Для worktree другого проекта сначала перейти в этот разрешённый проект через session_move.
Exit возвращает в canonical primary и не удаляет данные worktree. Из primary это no-op; недоступный или отозванный primary даёт отказ.

<a id="worktree-remove"></a>
## `worktree_remove {path}`

Адресно удаляет чистый незанятый attached worktree текущего проекта через native remove, без force (WT-06).
Запрещены primary, current cwd/содержащий worktree, цель живого сабагента, dirty/untracked, locked, detached и unavailable.
Ветка и коммиты сохраняются; остальные worktree не затрагиваются. Отказ не обходится через `rm`.
Межпроцессное владение других процессов omp — [F3](future-features.md#f3); v1 проверяет сабагентов текущего процесса и Git lock.

<a id="task"></a>
## Проект сабагента: `task.cwd`

Сохраняются штатные режимы task и все его параметры; wrapper добавляет только cwd (TASK-01). Поля агента seance (`sourceSession`, `model`, omp ≥ 18.11.3) доходят до preflight цели так же, как в нативном task.
При `task.batch=false` cwd находится в одиночном вызове; при `task.batch=true` — в каждом tasks[] item. Wrapper не включает batch сам и не рекламирует обе схемы одновременно.
`agent` должен существовать в назначенном проекте; worker в примерах — имя такого настроенного агента.
В режиме планирования отсутствие `isolated` сохраняется как отсутствие параметра; ограничения штатного task на явно переданные controls действуют без изменений.

```json
{"agent":"worker","task":"Проверить обработчик B","solutionSpace":"mechanical","cwd":"/workspace/B"}
```

Batch требует общий context и отдельные assignments; top-level cwd не допускается:

```json
{"context":"Сверить контракт A и реализацию B","tasks":[{"agent":"worker","task":"Исследовать A","solutionSpace":"mechanical"},{"agent":"worker","task":"Проверить B","solutionSpace":"mechanical","cwd":"/workspace/B"}]}
```

Без cwd фиксируется каталог родителя в момент вызова. Относительный cwd считается от него; абсолютный и `~` поддерживаются.
Непустые имена элементов пакета сравниваются после trim и приведения к нижнему регистру; дубли дают отказ всего пакета до артефактов и запуска модели.
Все цели и policy проверяются до запуска провайдера любого элемента. Контекст цели получает свои AGENTS, agents, settings, skills, rules, prompts, extensions/custom tools и MCP (TASK-02).
До первого запроса модели MCP цели должен завершить startup. Bridge ждёт готовности с собственным бюджетом 30 секунд; failed/pending дают отказ запуска сабагента и закрытие подготовленного manager. Это бюджет плагина, а не константа ядра.
Manager MCP цели создаётся при первом успешном task в эту цель и переиспользуется следующими вызовами до закрытия основной сессии. Правки `.mcp.json` цели между вызовами не подхватываются, как и у основной сессии без `/mcp reload`.
Проектные ресурсы и additional roots родителя не наследуются автоматически. Штатные async, output, progress и общий root concurrency limit сохраняются.
Общий лимит применяется к заданиям основной сессии; вложенные задания сабагентов используют собственный штатный лимит и не ждут уже занятого родителем semaphore.
Если расширение загружено также у сабагента, его обычный вложенный task остаётся штатным и не получает cwd. Назначать другой проект через task.cwd может только основная сессия.

Цель, настройки и artifact/journal anchor сохраняются при main move, session switch и park/revive (TASK-03).
`isolated:true` использует выбранную исходную цель; временный sandbox не меняет её canonical bank identity (TASK-04).
Mnemopi сабагента имеет отдельный backend, даже при общем банке с основной сессией. Startup заканчивается до первого запроса модели; обязательная ошибка не переключает память на родителя (MEM-02). Ошибка не окончательная: каждый следующий запрос сначала повторяет старт и блокируется, только если повтор тоже не удался.
Автоматический transcript-retain сабагента выключен; явные записи идут в банк цели (MEM-03).

<a id="memory-clear"></a>
## Очистка памяти Mnemopi

Штатные `/memory clear` и `/memory reset` используют backend текущего банка. Если другая живая сессия текущего процесса владеет открытой базой, входящей в выбранный scope, очистка отклоняется до закрытия или удаления данных.
Это касается primary/worktree одного банка и разделяемой global базы (MEM-02, MEM-03). После закрытия владельцев очистка разрешена; состояние вызывающей сессии создаётся заново с прежней project identity.
Проверка использует фактически открытые DB paths остальных агентов. Полная очистка и startup нового состояния сериализованы, чтобы параллельный startup не открыл базу между проверкой владения и удалением.
