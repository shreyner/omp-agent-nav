# Какую проблему решаем

Задача агента может охватывать несколько проектов и рабочих веток, а сессия omp имеет один cwd и связанный с ним контекст.
Bash `cd` меняет только процесс команды. Смена пути файлового инструмента не обновляет автоматически инструкции, настройки, MCP, LSP и память всей сессии.

Агент может править другой checkout, читать инструкции A во время работы в B, записывать опыт в чужой банк и запускать сабагента в родительском проекте вместо назначенного.
Человек вынужден менять сессию вручную и повторно объяснять задачу. Нужна смена среды с сохранением session ID и истории.

## Пользовательские сценарии

| Сценарий | Результат v1 |
|---|---|
| Основной агент A → B → A | Сохранены session ID и история; новый cwd, хранилище сессии, инструкции, настройки и память видны следующему запросу модели. |
| Создать ветку для правки | Чистый worktree от ref/HEAD без переноса изменений primary. Отдельным вызовом агент входит в него. |
| Человек просит `.claude/worktree/PROJ-123_fix` | `path` соблюдается точно; относительный путь вычисляется от primary, сам worktree исключается локально из его status. |
| Удалить завершённый worktree | Удаляется только выбранный чистый и незанятый worktree; его ветка и коммиты сохраняются. |
| Основной агент A поручает работу сабагенту B | Сабагент загружает ресурсы B и его память до первого запроса модели. |
| Сабагент стартует в worktree B или с изоляцией из B | Использует инструкции выбранного checkout и общий проектный банк B. |
| Основной агент переезжает в C при работающем B | Каталог, банк и журнал B сохранены, включая park/revive. |

## Исходный omp и выбранное решение

Исходная версия — опубликованный omp v18.10.3. Он предоставляет управление сессией и хранилищем, Settings, VCS/worktree, исполнитель task и Mnemopi.
В этой версии нет готового `task.cwd` и общего агентского workspace API; исходный task ориентирован на родительскую сессию, память сабагента ссылается на её backend.
Источники и подтверждённые наблюдения находятся в [verification.md](verification.md#baseline).

V1 использует локальное расширение, подключаемое через конфигурацию обычного установленного omp. Для host-операций применяется штатный import shim bundle; отдельного launcher и копии CLI нет.
Mnemopi и renderer используются как библиотеки установленного пакета с явными связями к host. Проверки source-entry launcher остаются историческим baseline; текущий способ подтверждается отдельно.
Поставка принимает omp >= 18.11.0 в том же major (проверенная матрица 18.11.0–18.12.2; миграция с 18.10.3 — 2026-10-15, матрицы — 2026-10-16/17/18; диапазонная политика — решение пользователя 2026-10-18): версии вне матрицы того же major грузятся с warning о непроверенности, ниже 18.11.0 и следующий major отклоняются явно.

Пользователь принял сохранение загруженных JS/TS extensions/custom tools основной сессии при переезде. В v1 обновляются AGENTS, settings, skills, commands, MCP, LSP, хранилище сессии и память.
Полная смена исполняемых фабрик основной сессии отложена в [F7](future-features.md#f7); известное последствие описано в [TD-01](tech-debt.md#td-01).

## Критерии успеха

- Операция навигации применяется после пакета инструментов и до следующего запроса модели; queued не выдаётся за applied.
- История и session ID сохраняются. Ошибка перехода восстанавливает исходные хранилище и контекст; ошибка восстановления останавливает модель.
- Смешанный пакет не выполняет ни move, ни write. Навигация запрещена сабагентам и вложенным вызовам.
- Создание соблюдает path/ref, не очищает исходные изменения. Удаление сохраняет данные изменённого, занятого или недоступного worktree.
- Primary и новые worktree имеют общий проектный банк; B изолирован от A. Сабагент владеет отдельным backend и не закрывает чужие ресурсы.
- Работа подтверждается тестами штатных механизмов и отдельными интеграционными проверками режимов и LSP, с явной границей доказательства.
- Расширение загружается обычным omp через `extensions` или `-e`, без отдельного launcher, копии CLI и изменения установленного пакета.

Посещение каталога не создаёт разрешение, а доступ к B не превращает память A в банк B. Разрешения и принадлежность памяти проверяются независимо.
